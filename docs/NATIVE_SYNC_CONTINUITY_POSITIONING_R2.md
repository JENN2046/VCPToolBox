## 1. 一句话定位

**NativeSync = VCP 原生跨终端连续性服务（Continuity Service）。**

它连接 VCPChat、VCPToolBox 和移动终端，让一个用户能够在不同设备之间接续同一 Agent 的交流及其已提交工作；Windows 不在线时，由 Ubuntu 继续执行已经被云端正式接受的工作。

NativeSync **不是**第二个聊天客户端、第二套 Agent/工具调度框架、第二个长期记忆系统，也不负责取代 VCPChat 的 History / Stream 权威与 AgentAssistant 的异步委托终态。

成功标准是减少设备边界，而不是扩大 NativeSync 自己拥有的业务规则。

## 2. 决定性的产品前提

1. **一个用户，顺序切换主动输入终端。** Windows、手机及其他终端是同一人的接续窗口。多个人类终端故意同时编辑或发送，不属于日常产品需求；无需围绕这种竞争使用方式建设复杂的自动仲裁机制。
2. **多个 Agent 与后台任务可以正常并发。** 用户切换终端时，AA 委托、群聊成员任务、插件执行、迟到回调仍可能持续；其任务 ID、结果归属、授权与终态必须准确，不得当成另一个人类终端的并行输入。
3. **Windows 保持 Local-First。** 原生流式聊天、本地 History、桌面专属 Canvas / WorkSpace / 文件工具保留原有运行方式；不能为了跨端接续将 Windows 强制改造成每次写盘都依赖云端的瘦客户端。
4. **Ubuntu 承担云端已接受工作的持续执行。** 只有云端已正式接受，或者通过明确交接移入云端的任务，才能在 Windows 关闭后继续；Windows 本地未移交的在途工作不被虚构成仍在云端运行。
5. **异常并发、重放及断网仍需安全。** 不把双终端同时操作当作主需求，并不代表可以丢弃幂等、冲突保护、重连恢复和执行副作用门禁。

## 3. 最终组成

| 组件 | 定位与职责 | 不拥有的职责 |
| --- | --- | --- |
| VCPToolBox / NativeSync Service（服务插件） | Ubuntu 常在线接续入口，持久化跨设备消息事件、请求 ID、恢复游标和云端执行任务状态；调用原生模型和工具链 | 不另造 ChatCompletionHandler、OneRing、AA 或通用聊天内核 |
| VCPChat / NativeSync Bridge（分布式服务插件，必要时最小原生合同） | 读取原生消息提交事实、传递增量操作、处理离线 Outbox、将远端事实安全物化至本机 history.json，并通知现有 UI / CDS | 不替换原生 ChatManager、StreamCoordinator、HistoryMutationAuthority、Flowlock |
| 移动终端（现阶段 PWA；以后可用于 VCPMobile） | 用户输入、历史展示、任务进度、结果查看及终端接续 | 不自行裁决 Agent/AA 的任务终态或重复执行复制来的历史 |
| 现有原生能力 | OneRing 管认知时间线；AA 管异步委托；ChatCompletionHandler 管模型/工具；VCPChat 管桌面消息与流式生命周期；CDS / VCPMobileSync 管其已提供的本地索引与同步能力 | 不要求 NativeSync 在旁路重复实现它们 |

**实现形态：两个尽量独立的插件/适配器 + 一种可复用的移动接入面 + 仅在必要时增加的最小、明确的宿主接入合同。**

“最大程度插件化”是维护目标，**不是已经证明的 Zero Core Diff 承诺**；不以运行时 monkey patch 伪装稳定的原生消息权威接口。

## 4. 仅保留三项核心能力

### A. Conversation Continuity｜会话接续

- 传递真实的消息新增、修改和显式删除操作，保留稳定 msgId、角色、顺序、Checkpoint、必要元数据及附件引用。
- Windows 自己创建的消息首先遵守原生 History / Stream 提交与完成规则，再提供给远端复制；手机提交的消息先由云端受理，再在 Windows 恢复时物化为原生历史。
- 中央 SQLite Journal 保留为**接续事件、已接受移动消息及恢复进度的持久账本**。不能仅凭它存在就宣称已取得所有原生 Topic 生命周期权威。
- **同步副本不得触发第二次模型请求、工具调用或第二个终态。** 不从全量数组缺少某个 ID 推断删除；旧快照不能静默覆盖新事实。
- 对最终一致性的边界保持诚实：不同终端本地写入与云端接收可以暂时不同步；尚未证明网络分区期间全局强一致，不能宣称具有这种能力。

### B. Execution Continuity｜执行接续

- 云端正式接受的请求绑定持久 requestId / executionId，调用原生 ChatCompletionHandler、ToolBox 工具和 AA 机制，客户端离线不自动取消已接受的任务。
- 严格区分普通模型回复完成、插件工具完成、AA 委托完成、整体任务终态；AA 回调只根据可信任务关联更新对应任务，不将任意 plugin-callback 盲目转换为新的 Assistant 消息或执行授权。
- 记录失败、取消、待确认外部副作用与恢复动作；不自动重跑结果未知的外部工具，不把可能重复执行称为 exactly-once。

### C. Device Continuity｜终端接续

- 用 Cursor、稳定操作 ID、Outbox / ACK 和任务查询恢复设备切换前的已提交结果与未完成状态。
- Windows → 手机 → Windows 是首要验收流程。用户输入通常按顺序发生；可有轻量的输入端接续状态，但它**不是**分布式租约或历史裁决的替代品。
- 断网和丢 ACK 时应可查询、幂等核对并安全重试；真正冲突时保留事实与诊断，不自动 LWW 静默覆盖。
- Windows 重上线后可恢复本地原生历史、附件引用、任务进度和已确认的迟到结果。

## 5. 与作者上游的边界

1. **OneRing** 维护同一 Agent 跨入口的近期认知事实；不是 VCPChat history.json 文件事务或 AA 任务调度的直接替代。
2. **VCPChat** 的原生 History、Stream、TopicSponsor、Flowlock 与群聊语义保持独立，由各自原生权威宣布完成；NativeSync 仅接收、传递、投影它们合法产生的事实。
3. **VCPMobileSync / CDS** 已有原生同步、索引、消息指纹与墓碑合同，应优先验证复用范围，不无依据地声称可直接跨越 Windows 离线宿主问题。
4. 原生接口不足时，可在下游 Fork 维护**最小、可验证的稳定接入点**。不因追求名义上的“零核心文件修改”而接管私有字段、猴子补丁或绕过原生保存语义。
5. 是否被上游 PR 接纳，不作为当前下游产品架构的先决约束；若提交上游，仍独立服从作者维护边界。

- 消息级增改删的原生提交入口与显式删除，不再从快照缺项推断墓碑；
- 过期全量替换的冲突处理、单条 409 与独立 Outbox 后续操作的恢复；
- Windows 原生 Stream / History 与移动消息复制之间没有错误重写或重复执行；
- AA 任务 ID、回调结果与相应 Topic / Execution 的可信关联及终态投影；
- Windows 真正离线、手机接续、多 Agent 后台工作、Windows 恢复后的实际一致性。

## 7. 最小端到端验收

1. Windows 在原生单 Agent 话题发送 U0，确认已有本地历史和可核对的同步状态。
2. Windows 客户端关闭；手机读到已确认的历史及任务状态。
3. 手机通过 Ubuntu 提交 U1 / U2，两轮均取得不同、可追溯的请求 ID，云端原生执行产生 A1 / A2。
4. 在云端触发一次真实 AA 异步委托，正确跟踪其完成回调和原始请求关联，不重复发起工具。
5. Windows 恢复后，原生 history.json 与 UI 接续 U0 / U1 / A1 / U2 / A2 及 AA 对应状态；内容、元数据、附件引用不误删、不重复、不静默覆盖。
6. 补测丢 ACK、重复发送、重启、中断和迟到结果；同一请求不重复执行已发生的外部副作用。
7. 不以用户故意在多个终端同时操作作为日常主路径；网络或程序制造的重复、冲突仍必须显式处理。

## 8. 下一步开发收敛（只三件）

1. **历史操作与恢复**：明确 msgId 级新增/修改/删除语义，取消隐式墓碑，避免过期整表覆盖，解开 409 Outbox 队头阻塞且保留冲突证据。
2. **顺序终端接续**：Windows → PWA → Windows，核对请求 ID、云端正式接受、离线 Outbox、Checkpoint、恢复与原生历史显示。
3. **原生异步状态关联**：将 AA / 工具执行结果准确关联到已接受的 Execution，按原生终态和授权规则投影，不建立平行的 AA 调度内核。

后续附件、群聊和 UI 优化按既有成果逐步复验，不得在权威合同尚未闭合时继续无边界扩展 NativeSync。
